## 3. 核心规则（改动前必读）

### 3.1 时序轴只有三种条目

`turn`（单位的行动机会）、`card`（挂刻引爆）、`aura`（预留）。

敌人的「行动机会」与「出招」是同一件事，所以没有单独的 `enemyMove` 类型 —— 它要在那一刻出什么招，直接写在条目的 `label` 上（「失序使 · 重击 24」），界面不需要再从别处拼信息。

### 3.2 同一行动值的结算顺序：挂刻 → 玩家 → 敌人

`TIMELINE_PRIORITY` 与「同为行动机会时玩家先手」共同定义了这个顺序。这是全局最重要的一条规则，也是「校正」类牌存在的全部理由：把敌人的行动推后到与你的挂刻同一时刻，挂刻会赶在它前面引爆。

规则一旦漂移，所有卡牌的相对价值都会变，所以它被 `tests/engine.test.ts` 钉死。

### 3.3 开局排轴：玩家在 0，敌人各在自己的一个间隔之后

曾经的做法是所有人从 0 行值起跑，结果两个敌人在开局同时出手、快速的那个还在同一回合再动一次 —— 实测第一回合就挨 4 次攻击、稳定度从 70 掉到 33，整局变成死亡螺旋，群战胜率直接从 43% 归零。让玩家先手、敌人按步频错开进场之后曲线才有中间档。

### 3.4 引擎是分步驱动的

```ts
const battle = createBattle(input);
battle.pending()                                  // 开场事件
battle.playCard(uid, target) → { events, result } // 界面拿去播
battle.endTurn()              → { events, result } // 推进到下次轮到我方
```

不是「一次算完整场」：那样界面就没法让玩家在回合中间做决定。机器人/回放用一层策略包起来循环调用（`simulateBattle`），所以无头测试仍然是一行代码跑一整场，回放也只需录下动作序列。

### 3.5 引擎直接持有卡面

`BattleInput.deck` 传的是 `CardInstance[]`（uid + `CardDef`）。规则层因此完全不认识 content 层，可以在不加载任何内容的情况下测引擎 —— 这条被现有的分层守卫覆盖。

### 3.6 一个单位开始行动时，先排下一次行动，再结算这一招

**顺序不是风格问题。** `advance()` 在调用 `runEnemyTurn` 之前就把当前条目从轴上摘掉了，
所以如果等到结算完才排下一条，招式效果里的 `selfAv`（自身行动值提前）会找不到可挪动的条目
而**静默失效** —— 抢拍体的「加速 −30」与失序使的「倒拨 −40」就这样空转了整整一个里程碑，
而它们的招式轮转表还明明白白展示给玩家。玩家看到的是一条会撒谎的规则说明。

玩家回合用的就是这个顺序（`startPlayerTurn` 一开始就排下一次），双方必须对称。

相关的第二条：**时间轴操作的下限是 `now + 1` 而不是 `now`**（见 `avFloor`）。
下限取 `now` 时，一个「招式 av 很小、selfAv 很大」的敌人会把下一次行动钳在当前时刻，
于是在同一个行动值上反复出手、时钟再不前进 —— 战斗彻底卡死。

这两条都不在类型系统能表达的范围内，所以它们各有一条测试守着（`tests/engine.test.ts`
的「敌人的『自身行动值提前』真的会生效」与「招式 av 很小而 selfAv 很大的敌人也不会把时钟卡住」）。

### 3.7 每条事件分支都以 `return` 结束，末尾做穷尽检查

`BattleEvent` 的消费方（`ui/battle.ts` 的 `applyEvent`）用 `const unhandled: never = ev`
收尾，而不是 `default: break`。加这条之前，`draw` / `energy` / `turnEnd` 三类事件一直是
「有等待、无反馈」——玩家看着界面停了一下，什么也没看到；而这在代码里看不出来。
穷尽检查让漏掉一类事件变成编译错误。

## 4. 数值是测出来的，不是猜的
`tests/balance.test.ts` 按「遭遇类型 + 敌人数量」自动分档，每档 40 局固定种子。

当前曲线：

| 档位 | 遭遇 | 胜率 |
|---|---|---|
| 单只普通怪（教学局） | 碎屑体 / 迟滞体 / 抢拍体 / 锈蚀体 | 100% / 100% / 98% / 100% |
| 群战普通怪 | 碎屑双生 | 100%（4.3 回合的消耗战） |
| 精英 | 锈蚀与碎屑 | 40% |
| 首领 | 失序使 | 23% |

机器人只按牌面价值贪心出牌、从不做时序规划，所以这些数字是**人类表现的下界**。

**调数值前请先读 `docs/卡牌设计指南.md`，并跑一次 `DIAG=1 npx vitest run tests/diag.test.ts` 把一整场逐回合打出来看。** 汇总数字只告诉你「有没有问题」，看不出「问题出在哪一段」。

三条来自实测的教训（都已经写进内容文件的注释里）：

1. **纯操作时间轴的招式会让难度塌掉**。失序使原本只有一招带伤害，实测胜率 98%，比精英还容易打。敌人的时间轴操作必须是伤害之外的附加手段，不能取代伤害本身。
2. **永久生效的易伤是乘算放大器**。锈蚀体原本每两回合刷新 1 层、每回合只衰减 1 层，等于整场 ×1.5；有它在场的双怪组合伤害直接翻倍，精英胜率从 40% 掉到 0%。易伤因此保留为**玩家的**手段，敌人改用推后行动值施压。
3. **双怪不能是「双强」**。玩家的每回合格挡是有限定额，两只满编怪一回合打出的量越过他能承受的上限时，胜率会从 100% 一步跌到 0%，没有中间档。群战档必须用「强 + 弱」或双弱。

## 5. 界面约定

- **时序轴**是战斗界面最重要的元素。`layoutChips` 是纯函数（输入条目与尺寸、输出像素位置），所以「同一时刻的条目会不会叠在一起」这类问题不需要浏览器就能测
- **战斗界面持久化 DOM**：`.battle-axis` / `.battle-body` / `.battle-hand` 每次同步重建，`.battle-fx`（飘字与震动）**只增不减**，否则动画会在下一帧被抹掉
- 所有动效走 `animate()` 包装，因为 jsdom 不实现 Web Animations API，而界面冒烟测试跑在 jsdom 里
- **字号下限 13.5px**、舞台 1440×720、时序轴宽度 `AXIS_WIDTH` 与 CSS 一致 —— 都由守卫测试断言

## 8. 版本号约定

四处必须同步：`package.json` 的 `version`（经 `define` 注入界面）、`package-lock.json` 的根 `version`、`android/app/build.gradle` 的 `versionName` 与 `versionCode`、以及 git tag。前三处的同步由守卫测试断言。

锁文件那处一度被漏掉，_root version 悄悄停在旧号上很久没人发现 —— 它不影响安装，但会让「版本号到底有几处」说不清楚。同步用 `npm install --package-lock-only`，不要手改。

`versionCode` 漏加会导致侧载更新不被识别 —— 这是个已经踩过的坑。

发布流程：

```bash
git tag v0.2.0
git push origin v0.2.0
gh run watch
gh release view
```

## 9. 安全与供应链

### 代码层的既有性质（不是靠约定，是靠结构）

- **没有注入面**：界面只用 `textContent` / `createTextNode` 写文本，从不拼 HTML。唯一的 `href` 是编译期常量加 `rel="noreferrer"`。这条现在由守卫测试守着 —— 禁词清单本身是拆开拼装的，否则扫描器会把「列出禁词的清单」误判成「用了禁词」
- **唯一的用户输入**（种子输入框）在离开 `parseSeed` 前就被归一化成 `uint32`，任何字符串都不会流到 DOM 写入
- **不发网络请求、不写任何存储**：构建产物里唯一的 `fetch` 是 Vite 的 modulepreload 垫片，读的是自己的分块。`INTERNET` 权限是 Capacitor 模板带的，代码里没有任何地方用到
- **src 里没有 Node API**：那里只有浏览器与 WebView。tsconfig 为了让 `tests/` 能读文件而引入了 `node` 类型，所以这条边界由守卫测试来守

### 供应链上的三处硬约束

1. **Actions 全部钉在完整 commit SHA 上**，不用浮动 tag。浮动 tag 是可被上游随时重指的可变引用，被重指时 workflow 文件不会有任何变化，跑的却是别人写的代码。升级时连同注释里的版本号一起改
2. **写权限只给真正需要写的 job**。`android-build.yml` 拆成两个：构建 job 是 `contents: read`，只有下载产物并发 Release 的 job 才拿 `contents: write`
3. **Gradle 发行包声明了 `distributionSha256Sum`**。没有它时 `validateDistributionUrl` 只校验 URL 格式，下载到的 zip 会被直接解压执行。`gradle-wrapper.jar` 的 SHA-256 也记在守卫测试里 —— 它是仓库中唯一被追踪的二进制可执行文件，也是典型的供应链攻击目标

### 凭据

签名密钥、`.env`、`google-services.json` 全在 `.gitignore` 覆盖内，两处 ignore（根目录与 `android/`）都写了。处理规则见 [CONTRIBUTING.md](../CONTRIBUTING.md) 的「凭据与签名」。

目前**仓库里不存在任何密钥**：CI 只出 debug APK，用 Android 默认调试密钥签名。正式发布要换 release 签名时，密钥放仓库外、密码走 Actions secrets。

### 刻意没有改的一处

`android:allowBackup="true"` 保持原样。M2 会有存档，届时让存档能随设备迁移是**产品上想要**的行为；现在改成 `false` 是把一个产品决策当安全问题处理。这条留到 M2 连同存档一起定。

### 另一个留给 M2 的设计缺口

**没有行动值或回合上限，玩家可以无限拖局。** 只出守刻（5 点格挡 × 3 点能量 = 15）就能一直挡住碎屑体（每 100 行动值约 13 点伤害），时钟可以无限往前走。

这不是缺陷而是缺口：M1 只有单场战斗，玩家主动选择不打就没有输的理由；但 M2 的单局结构本来就需要回合上限（同类项目用的是倒计时），否则「拖到天荒地老」会成为最优解。**现在不发明机制** —— 它要和地图、奖励一起设计才有意义。

### 已知的覆盖边界

- Release 那条路径（`android-build.yml` 的 `release` job）只在推送 `v*` tag 时才会执行，日常 CI 不会碰到它 —— 也就是说它是**未被 CI 覆盖的一段**
- `softprops/action-gh-release` 是本项目唯一的第三方 action，虽然已钉 SHA，但它的行为本身没有在本地验证过
- **`android:allowBackup="true"` 与「无回合上限」两处已记录的决策**（见上一节），都不是遗漏而是留给 M2 的选择
- 界面冒烟测试跑在 jsdom 里，它**看不到任何视觉效果**：布局死区、字号观感、层级遮挡这类问题只有截图验收能发现。所以改界面之后请照 `CONTRIBUTING.md` 的界面约定走一遍截图自查
